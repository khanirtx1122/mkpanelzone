# 2026-09-23 — Premium redesign of MK PANEL ZONE

## Scope

Visual/UI/UX transformation per `Prompt.md` (66 sections): premium storefront, editorial product
pages, cinematic-but-restrained hero, three-surface customer access, admin "control room", and a
fast agent workstation. Constraint throughout: **do not break working functionality or weaken
security**, and **do not fake anything** (no fake analytics, fake progress, or dead controls).

## Security remediation (the major finding)

The entire admin panel was **unauthenticated**:

1. `ensureOwner()` in `src/app/mkpanelzoneadmin/actions.ts` was a stub returning a fake owner.
2. `src/app/mkpanelzoneadmin/layout.tsx` performed **no session check** — only a display-name lookup.
3. Inline `"use server"` actions in all 7 `[id]` editor pages had **no check at all**, one carrying
   `// Bypass owner check for UI testing as requested`.
4. No `middleware`/`proxy` and no `.env`.

Net effect: every customer record (identifiers, payment proof, device hashes) was publicly readable,
and 14 privileged actions were invocable anonymously.

**Fix (per user decision: "restore, dev-only bypass"):** new `src/lib/ownerAuth.ts` exporting
`requireOwner()`, which validates the httpOnly `owner_session` cookie **against the database**
(role `OWNER` + status `ACTIVE`) and fails closed on DB error. Bypassed when
`NODE_ENV !== "production"` because there is no `.env` so `OWNER_BOOTSTRAP_TOKEN` is unset.
Wired into the layout (redirect to `/mk-agents`, amber "Dev · auth bypassed" pill), `ensureOwner()`,
and all 15 inline editor actions. Also added defence-in-depth status re-checks to
`agentCreateCustomer` and `createAgent`.

## Bugs found and fixed (pre-existing, not introduced by the redesign)

- **`redirect()` inside `try`** — `redirect()` throws, so the `catch` swallowed successful saves and
  redirected them as failures. Present in all 7 admin `[id]` editors. Also in `managementLogin`,
  where a fragile `error.message.includes("NEXT_REDIRECT")` sniff was the only thing making sign-in
  work. Moved every redirect after its `try/catch`.
- **Fabricated upload progress** — `AdminVideoUploader` animated `setProgress(p => p + 5)` on a
  timer. Replaced with genuine XHR byte progress.
- **"Click or Drag" with no drop handler** — drag-and-drop was advertised but not implemented.
- **`customer.status` enforced nowhere** — the owner panel's "Disable customer" toggle was purely
  decorative. Now checked in `customerLogin` (new `ACCOUNT_DISABLED` result, after password
  verification so it can't be used to probe identifiers), in `/dashboard`, and `/access` no longer
  auto-redirects a disabled session into a loop.
- **`agent.status` not checked in the agent layout** — a disabled agent kept their session.
- **Agent detail page reported capped figures** — "Total Customers" came from a `take: 50`
  relation, so an agent with 300 customers showed 50. Replaced with `count` + `groupBy`. iOS was
  also missing from the platform breakdown.
- **Activity page under-counted** — "changed in 24h" was derived from the 30 displayed rows; now a
  real `count` over the whole table.
- **"Last Updated" showed today's date** on privacy/terms (`new Date()` per render) → fixed constant.
- **Support page buttons were not links** (`<button>` with no handler).
- **`e.currentTarget` read after `await`** in `mk-agents/page.tsx`.
- **Video URL was unconfigurable** — the video field only allowed file upload, so
  `demoVideoType: YOUTUBE` could never be set. Added a paste-a-URL path.

# ART DIRECTION CHANGE (same day, after user feedback)

The user rejected the restrained-SaaS direction as reading like generic AI dark-mode and supplied
three references: **alche.studio**, **zrk.technology**, and the awwwards 3D collection. Their
shared DNA, which now drives the design:

1. **Near-monochrome, very high contrast.** Colour lives in the imagery; the interface is
   achromatic. Black base, near-white type.
2. **Enormous display typography** — headings at 100px+, tight leading/tracking, deliberately
   broken across lines.
3. **A technical monospace annotation layer** — `01 / 05`, `//`, `};`, `UNIT COST: …`. This is the
   single most identifiable signature of that aesthetic.
4. **Editorial/ledger structure** — dated indices, hairline rules, numbered readouts, heavy
   negative space.

Two decisions were taken by the user via AskUserQuestion:
- **Palette:** near-monochrome, brand colours survive only as *rare* purposeful accents.
- **3D:** real WebGL via React Three Fiber (not CSS 3D, not canvas 2D).

## What changed

**Palette (highest leverage — `globals.css`).** The old surfaces were blue-tinted
(`#070A0F`/`#0B1018`/`#101722`) and the ambient washes were blue and crimson radial gradients
painted behind whole sections. That colour cast is what made the app read as generic. Now:
neutral greys (`#050506`/`#0A0A0B`/`#101012`/`#17171A`), white-alpha hairlines only, neutral ink
tiers, and **achromatic** ambient washes. Light theme likewise de-tinted (was `#F2F5FA` + slate).

**One accent.** `--accent` / `--accent-strong` / `--accent-text` / `--accent-soft` /
`--accent-border`, with a documented permitted-use list: the primary CTA, the active indicator,
focus rings, and the info status. Nothing else.

**Type.** Added a fluid display scale (`--text-display-xs` … `--text-display-xl`, up to
`clamp(4.5rem, 16vw, 15rem)`) and `.display` / `.display-tight` / `.text-outline` classes.
`.text-outline` uses `-webkit-text-stroke` inside `@supports`, with a plain-colour fallback so
text is never invisible.

**Annotation layer.** `src/components/ui/Tech.tsx` — `TechLabel`, `TechIndex`, `TechRule`,
`SectionMarker`, `TechMarker`, `DisplayHeading`, `TechStat`, backed by `.tech*` classes with
tabular numerals.

**WebGL.** `src/components/three/HeroScene.tsx` (the scene) + `HeroCanvas.tsx` (the gate).
A receding lattice of panel outlines — on-brand, genuinely 3D, and **one draw call** (all 1144
vertices in a single `LineSegments` BufferGeometry). The **scene** moves and the camera stays
fixed, because mutating `camera` from `useThree()` is flagged by `react-hooks/immutability` and
translating the group gives the same parallax with the panels kept frontal.
`HeroCanvas` refuses to load on `prefers-reduced-motion`, `data-perf="low"`, `saveData`, or
without WebGL, and dynamically imports the scene with `ssr: false` so three.js never enters the
initial bundle. Capability is read through `useSyncExternalStore` (not `setState` in an effect).

**De-slopping sweep.** Three scripted passes replaced, across ~50 files:
- decorative blue/crimson radial washes → `var(--ambient-blue|--ambient-strong|--ambient-crimson)`
- hardcoded slate hairlines → `var(--border-subtle)`
- the recurring "blue icon tile" (`border-brand-blue-500/25 bg-brand-blue-500/10
  text-brand-blue-400`) → neutral — 145 replacements
- decorative hue rotation removed entirely: `ProductCard`'s blue/crimson/steel cycle,
  `PlatformCard`'s per-platform hues, `page.tsx`'s tone ternaries, `FeaturedProductsSection`'s
  crimson/blue alternation, `SectionHeading`'s accent rule
- focus rings tokenised to `outline-[color:var(--accent)]` (a permitted use)

# FALSE "ONE DEVICE, ENFORCED" CLAIMS — CORRECTED (12 sites)

Having fixed the footer's "device-bound access" line, I grepped for the claim
everywhere and found it repeated across the **entire public site**. The product's central
trust proposition rested on a mechanism that does not exist.

Sites corrected:
| File | Was |
|---|---|
| `app/page.tsx` (hero trust list) | "Device-bound access" |
| `app/page.tsx` (why-us card) | "Device-bound access" / "cryptographically tied… Sharing an account fails at the server, not in the browser" |
| `app/page.tsx` (section intro) | "every package is bound to one device" |
| `app/page.tsx` (platform section) | "Device-bound access" |
| `app/products/page.tsx` | "bound to a single device" |
| `app/products/[slug]/page.tsx` | "bound to one device… enforced on the server, not in the browser" |
| `app/checkout/[slug]/page.tsx` | "One account, one device" |
| `app/order/success/page.tsx` | "Access bound / One account, one device." |
| `app/support/page.tsx` (FAQ) | "bound to one device and enforced on the server" |
| `app/terms/page.tsx` | "cryptographically bound to one device" |
| `app/agent/create/page.tsx` | "bound to one device and enforced on the server, not in the browser" |
| `lib/productContent.ts` (FAQ) | "strictly bound to the first supported device… permanent ban" |

**The distinction applied.** A *policy* statement ("one account, one device", "single-user
licence") is legitimate — policies are enforced by people, and the admin panel genuinely has
`adminResetCustomerDevice` so support really can transfer a binding. A *mechanism* claim
("enforced on the server", "fails at the server", "cryptographically tied", "not in the
browser") is not, and every one of those was removed. The copy now states the policy plus the
real support path: *"If you change hardware, contact support and we will transfer the access."*

One claim was kept and verified: "Platform access is enforced on the server — you can never
reach another platform's resources." That is true — `customerLogin` returns `WRONG_PLATFORM`,
and `dashboard/page.tsx` scopes its resource query by `customerType`.

## Still open — the one decision that remains

**Device binding is recorded, not enforced.** A `device_token` is minted on first sign-in and
stored hashed, but it is never verified on later logins, and `DEVICE_MISMATCH` is returned by no
code path. The copy no longer claims otherwise, so the site is honest — but if the owner wants
the *policy* to be technically enforced, the change belongs in `customerLogin`'s
`else` branch (compare the presented `device_token` against `customer.devices[].deviceTokenHash`
with `argon2.verify`) and should be gated behind an off-by-default `SiteSetting` so nobody is
locked out until it is deliberately switched on. Not implemented — it risks locking out paying
customers who have cleared cookies, and that is the owner's call, not mine.

## GOTCHA — a stale Turbopack cache produces a spurious CSS syntax error

For a while `next build` failed with:

```
CssSyntaxError: tailwindcss: src/app/globals.css:2:34435: Missed semicolon
```

`globals.css` was **fine**. Three checks proved it: braces balanced once comments were stripped,
PostCSS parsed it, and `@tailwindcss/postcss` compiled it standalone with no error.

The real cause: earlier builds had been killed mid-write (one by `TaskStop`, several by the
sandbox bulk-delete guard), leaving a **corrupted `.next` cache**. Compounding it, my
`mv .next .next-old-$$ 2>/dev/null` was failing silently — stderr was suppressed — so the stale
cache was never actually moved aside and the error survived every "clean" rebuild. `ls -d .next*`
eventually revealed three leftover directories.

**Lesson:** when a build error points at a file you can prove is valid, suspect the cache. And
never suppress stderr on the cache-clearing step — `mv .next … 2>/dev/null` hid the failure for
several rebuilds. Clear with `rm -rf .next` and confirm it is gone before rebuilding.

After clearing: **`✓ Compiled successfully in 29.0s`**, all 9 static pages generated, fresh
`BUILD_ID`, every route bundle present. The only remaining failure is the sandbox's bulk-delete
guard at the final cleanup step.

# DEVICE ENFORCEMENT IMPLEMENTED — OPT-IN, OFF BY DEFAULT

The last open item is closed. The policy is now technically enforceable without any risk of
locking anyone out, because it ships **switched off**.

## What was built

**`src/lib/settings.ts`** — the read side of `SiteSetting`, which had been write-only.
- `getSettings(keys[])` — batch read for page-level settings. Returns `Record<string, string>`
  with **every requested key present**, absent ones seeded as `""`, so callers can fall back on
  falsiness. Errors propagate (callers already wrap it in try/catch and render designed
  fallbacks).
- `getSetting(key)` / `getBooleanSetting(key, fallback)` — single-key reads for hot paths, with a
  10s in-process memo. **Fails to the caller's fallback, never throws**, and deliberately does not
  cache the failure.
- `invalidateSetting(key)` — drops the memo.

**`customerLogin`** (`src/app/actions.ts`) — the `else` branch that had never existed. When a
binding already exists **and** `enforce_device_binding` is on, the presented `device_token` must
`argon2.verify` against one of `customer.devices[].deviceTokenHash`. No cookie, an unreadable
hash, or no match all deny with `DEVICE_MISMATCH` — it **fails closed**, never silently rebinding
to the new device. A successful match touches `lastUsedAt` so the admin can see which binding is
live. A malformed stored hash is caught per-device rather than aborting the whole check.

**Control Room → Settings** gained a "Device binding" group with the toggle, a live status line,
and an explicit warning that there is no self-service reset and existing customers who cleared
cookies will be locked out until an admin resets their binding.

**`proxy.ts`** now reads through the shared helper instead of carrying its own copy of the cache
logic, and **`saveSettings` calls `invalidateSetting`** so a toggle applies on the next request
rather than up to 10s later. The maintenance copy was corrected accordingly ("Changes can take up
to 10 seconds to apply" was no longer true).

## MISTAKE I MADE — clobbering an existing module

I wrote `src/lib/settings.ts` as a **new** file without checking whether it already existed. It
did, exporting `getSettings`, and eight files imported it. TypeScript caught it immediately
(`Property 'getSettings' does not exist`), and I reconstructed it from the call sites — including
getting the return type right (`Record<string, string>`, not `... | undefined`, which
`support/page.tsx` demanded).

**Lesson: check for an existing file before `Write`.** `Write` overwrites silently. The tool even
tells you to `Read` first when the file exists — I bypassed that by treating it as a new file.
A one-second `ls` or `Glob` would have avoided it.

## Final state of the device policy

The site copy is honest in **both** modes, because it states the policy plus the support path
rather than a mechanism. When enforcement is off: "the first device is recorded, contact support
to transfer". When on: the same sentence is now also technically true, and the
`DEVICE_MISMATCH` screen becomes reachable — its copy was corrected earlier, so it is ready.

# LINT CLEAN-UP — 89 problems → 0, and three more real bugs

`npm run lint` went from **89 problems (52 errors, 37 warnings)** to **0 problems**, with
`npx tsc --noEmit` clean. This was not cosmetic: clearing the rules surfaced three genuine bugs
that `any` and the disabled-effect pattern had been hiding.

## THE BIG ONE — no setting in the admin panel could ever be saved

`saveSettings` was declared:

```ts
export async function saveSettings(formData: FormData) { … }
```

but bound with `useActionState(saveSettings, null)`. **`useActionState` always invokes the action
as `action(previousState, formData)`** — so `formData` received `null`, `formData.keys()` threw,
the `catch` swallowed it, and every save returned "Failed to save settings."

`prisma.siteSetting.upsert` inside that function is the **only writer of `SiteSetting` anywhere in
the codebase**. So no setting had ever been persisted: site name, SEO, footer copy, support links,
`maintenance_mode`, and the `enforce_device_binding` toggle I had just built were all unsaveable.

This also **corrects an earlier conclusion of mine**: I had reported "the settings system is
write-only". It was not even writable. Every `getSettings` read has been returning `""` and every
caller has been silently using its fallback.

Fix: declare `prevState: ActionState | null` as the first parameter, plus a runtime
`formData instanceof FormData` guard so a future mismatch fails loudly instead of looking like a
database error. Then a shared `ActionState` type (`src/lib/actionResult.ts`) was applied to every
`useActionState` call and every action signature, so the hook and the action can no longer
disagree about the argument list.

## Removing `any` surfaced two more real bugs

- **`submitOrder`'s result was not a discriminated union.** Both branches had `success: boolean`
  (widened), so `if (!res.success)` narrowed nothing — which is *why* every consumer reached for
  `any`. Typing it as a proper union with literal `true`/`false` immediately exposed that
  `sessionStorage.setItem(key, res.whatsappUrl)` could store the string `"null"` when the owner has
  no WhatsApp number configured. The success page would then `window.location.assign("null")`.
  Fixed on both sides: the writer only stores a real URL, and the reader rejects a stored `"null"`.
- **An empty `catch (error) {}`** in `performCustomerStatusToggle` silently discarded failures.
  Now logged.

## Rules cleared

| Rule | Before | After |
|---|---|---|
| `react-hooks/set-state-in-effect` | 13 | **0** |
| `@typescript-eslint/no-explicit-any` | 22 | **0** |
| `react-hooks/static-components` | 3 | **0** |

Notable approaches:
- **`useIsClient`** (`src/lib/useIsClient.ts`) — replaces the `useState(false)` +
  `useEffect(() => setMounted(true))` hydration guard with `useSyncExternalStore`, which reads the
  same fact without scheduling a second render. Used by ThemeToggle, PremiumModal, ToastProvider,
  HeroCanvas.
- **External stores over browser storage** — AdminSidebar's collapsed preference (localStorage),
  AnnouncementBar's dismissal (sessionStorage), CinematicIntro's `data-intro` attribute, and
  SuccessAutoRedirect's one-shot read. Each uses `useSyncExternalStore` with a memoised snapshot;
  the read-once accessor must cache, because `getSnapshot` can be called more than once and the
  read *consumes* the key.
- **Adjusting state during render** — the documented React pattern, used for FilterBar's URL sync,
  the Navbar/AdminSidebar drawer-close-on-navigation, and the three "action succeeded" handlers.
  A `syncedX` guard makes it a single pass. The effects that remain own only genuine side effects
  (timers, `form.reset()`, toasts, `router.refresh()`).
- **`ProductIcon`** — `iconFor(slug)` returned a component, so `react-hooks/static-components`
  flagged three call sites (it cannot know the return is a constant). Replaced with a real
  component that renders literal elements.
- **17 silent `catch` blocks** now log their error. The codemod that did it had to strip property
  keys first: `return { error: "…" }` contains the word `error`, which gave a false negative on
  the naive "does the body use the binding" test.
